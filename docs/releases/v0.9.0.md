# v0.9.0: retained replay and reliable source lifecycles

Outpace AceStream 0.9.0 brings the 0.9 beta series into a stable version, based
on beta.8. This release preparation changes version metadata and documentation;
it introduces no additional runtime behavior or dependency updates.

## Playback and source lifecycle

- Public, unencrypted AceStream acquisition feeds native MPEG-TS and HLS, with
  shared source sessions for multiple viewers. The optional Ace HTTP
  compatibility routes expose the documented subset of the original API.
- Opt-in retained HLS history supports finite replay, independent viewer
  generations, explicit return to live and invalidation of superseded URLs.
  Live acquisition stays shared while each viewer controls its own position.
- Native HLS and compatibility manifest startup use one timeout across source
  acquisition and response preparation. A queued opener cannot receive a new
  full readiness budget after spending its startup allowance. Expiry returns
  HTTP `503` and `Retry-After: 1`; cancellation removes only the request's
  unpublished lease.
- Explicit stop, shutdown and manager destruction cancel source consumption
  even when callers retain session handles. Receivers can drain queued media
  before EOF, and idle cleanup preserves acquisition-to-subscription ownership.
- Clean source EOF exposes completed current-generation HLS media below the
  usual startup segment count once catch-up is complete. Partial tails,
  terminal failures and old recovery generations are not promoted. Finalized
  packagers release unused assembly storage.
- Live request scheduling preserves early Unchoke state, drains authenticated
  buffered pieces after cursor changes and can assign work to another peer
  when a command channel is full. VOD reissues outstanding requests after
  Choke-to-Unchoke without discarding coverage or extending progress deadlines.
- Playlist rendering writes directly into the output string while preserving
  formatting, pruning, segment grace and end-of-stream semantics. No measured
  throughput or latency improvement is claimed by the version promotion.

## History remains bounded and opt-in

History is disabled by default. Retention is constrained by elapsed time,
accepted media duration, segment count and per-source/shared byte budgets.
Snapshots do not pin media against pruning; an expired replay can return HTTP
`410`. A failed seek leaves the existing viewer state intact.

These controls provide replay of media already acquired by the current HLS
packager. They do not provide persistent DVR, UTC/EPG catch-up, recording of
inactive channels or recovery of media from before acquisition. Restarting or
removing a packager discards its history. The independent peer-history reader
remains experimental and is not a network archive exposed through the player
API. See the [timeshift contract](../timeshift.md) for limits and client duties.

Player or proxy integrations must retain the control session, issue a seek and
reload the returned URL. API and decoder tests alone do not establish Tauri,
LG, Fire TV or other device controls, codec support or perceptual smoothness.
Premium/encrypted sources and full closed-engine API parity remain out of scope.

## Packages, source and upgrade scope

The release workflow builds seven binary/source pairs: Windows x64 and ARM64,
macOS Intel and Apple Silicon, and Linux amd64, ARM64 and ARMv7. The container
index covers Linux amd64, ARM64 and ARMv7. Each binary is paired with complete
source, locked dependency sources, notices and rebuild instructions under the
retained AGPL-3.0-or-later terms. The service's source endpoints identify and
offer the matching embedded workspace source.

The stable tag is `v0.9.0`. Stable publication is eligible for the GitHub latest
release and container `latest` channel only under the existing release policy;
numbered beta artifacts remain separate. Use the versioned package or an
immutable image digest when upgrading, and preserve the previous verified
binary/image, source receipt, configuration and persistent identity for rollback.

This promotion adds no listener, DNS, authentication, history-budget or engine
default change. Installation recipes and example image selectors now target
0.9.0; verify publication and pin a reviewed image digest for production. The
beta series includes compatible dependency maintenance and keeps the reviewed
signing API dependencies together. Historical v0.8.1 migration caveats remain
explicit. See [installation](../installation.md),
[containers](../containers.md) and [Kubernetes](../kubernetes.md).

## Qualification and status

This page describes release scope, not completion of RC assessment, publication
or deployment. The existing manually requested [RC workflow](https://github.com/open-ott-play/outpace-acestream/actions/workflows/fuzz-candidate.yml)
assesses the exact default-branch source commit; it does not create an RC tag or
qualify release artifacts. There is no new `-rc` tag scheme.

Normal source tests, lint, synthetic media checks and release-policy tests must
pass. Publication must then verify the actual binary/source pairs and container
index. A deployment requires its own source/identity checks and bounded decoded
live/replay/return-live acceptance with cleanup. Earlier beta results are useful
evidence for their exact builds, not substitutes for these checks on 0.9.0.

The release page and workflow records carry the publication and assessment
status. No fixed cold-start time, universal channel availability, measured
speedup or new device compatibility is promised here. Earlier beta release
notes remain available in this directory.
